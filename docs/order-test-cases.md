# 订单接口用例设计

依据被测服务的 `app/api/orders.py` 和 `app/services/order_service.py`，先记录规则，再编写回归用例。`POST /orders` 使用当前登录用户的购物车创建订单，不需要请求体；成功后清空购物车并扣减商品库存。

| 编号 | 风险与优先级 | 前置条件和输入 | 操作 | 预期结果 | 数据处理 | 自动化位置 |
| --- | --- | --- | --- | --- | --- | --- |
| ORD-001 | 正常下单，P0 | 独立测试用户；新建唯一名称、单价 10、库存 2 的商品；购物车加入该商品 2 件 | `POST /orders`，再按返回 ID 查询订单、购物车和商品 | 创建返回 201；订单状态为 `PENDING`，明细数量为 2、总金额为 20；按 ID 能查回订单；购物车清空、库存减至 0 | 订单和扣减的库存没有 API 恢复路径；只在可重置的独立测试数据库运行，使用本次返回的商品和订单 ID | `tests/test_orders.py::test_create_order_from_cart` |
| ORD-002 | 空购物车下单，P0 | 新注册并登录的测试用户；购物车和订单列表均为空 | `POST /orders`，再次查询购物车和订单列表 | 返回 400，错误类型为 `http_error`、消息为 `Cart is empty`；没有创建订单，购物车仍为空 | 使用唯一用户名；服务没有删除用户的接口，账号会留在本地测试数据库 | `tests/test_orders.py::test_create_order_with_empty_cart` |
| ORD-003 | 已加购商品的库存被其他订单耗尽，P1 | 新建库存为 1 的独立商品；独立用户 A、B 各加购 1 件；A 先下单 | B 再调用 `POST /orders`，查询 B 的购物车、订单和商品库存 | A 创建返回 201；B 返回 400，错误说明库存不足；B 的订单未创建、购物车保留；商品库存为 0 | 两个用户使用独立 Session；仅清理各自购物车。A 的订单和商品无法通过现有 API 删除；在可重置测试库运行 | `tests/test_orders.py::test_order_rejects_stale_cart_stock` |
| ORD-004 | 其他用户读取订单，P0 | 独立用户 A 创建订单并保存本次返回的 ID；用户 B 没有订单 | A、B 分别调用 `GET /orders/{id}`；B 再查自己的订单列表 | A 查询返回 200 和原订单 ID；B 查询返回 404，订单列表为空 | 使用唯一商品和独立账号；仅清理购物车，订单及商品保留在可重置测试库 | `tests/test_orders.py::test_order_detail_is_hidden_from_other_user` |

ORD-003 是顺序执行的库存变化场景，不证明两个请求同时到达时的并发正确性。当前服务没有收货地址字段；地址缺失不属于这组订单接口的可执行用例。支付走独立的模拟支付接口，后续单独设计。正常下单及双用户用例会留下订单并改变库存，不能用“取消订单”代替数据清理。
